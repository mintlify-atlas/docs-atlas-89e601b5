Modern TypeScript and Next.js projects rarely use only relative imports. Path aliases like `@/components/Button` are far more common — they're cleaner, refactor-friendly, and avoid the `../../..` noise that makes large codebases hard to read. Without resolving these aliases, Flowy would see `@/components/Button` as an opaque string with no connection to any real file, breaking the dependency graph and leaving your mind map full of dangling, unresolvable import edges. Flowy automatically reads your repository's `tsconfig.json` to extract path alias mappings and resolve them to their actual file paths before building the graph.

## What are path aliases?

Path aliases are shortcuts defined in `tsconfig.json` under `compilerOptions.paths`. They map a prefix pattern to one or more real directory paths, allowing imports throughout the codebase to reference a stable short name instead of a fragile relative path.

A typical `tsconfig.json` with path aliases looks like this:

```json tsconfig.json
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@/*": ["src/*"],
      "@components/*": ["src/components/*"],
      "@utils/*": ["src/utils/*"]
    }
  }
}
```

With that configuration in place, source files can use the short alias forms directly:

```typescript src/pages/Home.tsx
import { Button } from '@components/Button';
import { formatDate } from '@utils/date';
```

Without alias resolution, Flowy would not know that `@components/Button` corresponds to `src/components/Button.tsx`. With it, both imports appear as proper edges in the mind map connecting `Home.tsx` to the files it actually depends on.

## How Flowy resolves aliases

When Flowy analyzes a repository, it performs alias resolution as an early step in the build pipeline:

1. **Detection** — Flowy scans the repository root for a `tsconfig.json` file. If one is present, it proceeds to extract alias data.
2. **Extraction** — Flowy reads `compilerOptions.baseUrl` and `compilerOptions.paths` from the configuration. These two fields together define the complete alias mapping.
3. **Resolution** — For every import statement encountered while parsing source files, Flowy checks whether the import specifier matches any alias pattern. If it does, the alias is substituted with the resolved real path before the dependency edge is created.
4. **Graph construction** — The mind map is built from the fully resolved dependency graph, meaning every node connection accurately reflects the true file relationship in the repository.

## Supported alias patterns

Flowy supports the full range of path alias configurations you're likely to encounter in real projects:

- **Wildcard catch-all aliases** — `@/*` mapped to a base directory such as `src/*` or `app/*`. This is the default pattern generated by `create-next-app`.
- **Named aliases** — Specific prefixes like `@components/*`, `@utils/*`, `@hooks/*`, each mapped to their own subdirectory.
- **Multiple aliases in a single tsconfig** — All entries under `compilerOptions.paths` are processed together; there is no limit to the number of aliases in a single file.
- **Monorepo nested tsconfig files** — Flowy makes a best-effort attempt to resolve aliases in monorepos by checking for `tsconfig.json` files in workspace package directories. If a package has its own `tsconfig.json` with a `paths` configuration, Flowy uses that file's aliases for files within that package's directory tree.

<Tip>
  Ensure your `tsconfig.json` is committed to the repository root (or to the relevant package root in a monorepo). Flowy reads it directly from the repository file tree — any file that exists only locally and is excluded via `.gitignore` will not be visible to Flowy's analyzer.
</Tip>

<Note>
  JavaScript projects without a `tsconfig.json` do not benefit from alias resolution. However, all relative imports (e.g., `./utils/date`, `../components/Button`) are still fully mapped and will appear as accurate dependency edges in the mind map. Only aliased imports will appear unresolved.
</Note>

<Accordion title="What if my tsconfig uses extends?">
  Flowy follows `extends` chains to reconstruct the full effective configuration before extracting alias data. For example, if your root `tsconfig.json` extends a shared base configuration stored at `tsconfig.base.json` or inside `node_modules` (such as `tsconfig/nextjs.json`), Flowy reads both files, merges them in the correct order of precedence, and uses the resulting `compilerOptions.paths` for resolution. This means alias definitions inherited from a shared base config will resolve correctly without any additional setup on your part.
</Accordion>

<Accordion title="Are jsconfig.json aliases supported?">
  Support for `jsconfig.json` — the JavaScript equivalent of `tsconfig.json` used in plain JavaScript projects — is on the Flowy roadmap. At launch, alias resolution is limited to `tsconfig.json`. Check the [Roadmap](/reference/roadmap) for the latest status on `jsconfig.json` support.
</Accordion>
