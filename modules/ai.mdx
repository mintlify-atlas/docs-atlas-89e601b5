The Integrated AI module turns your mind map from a passive diagram into an active analytical partner. Instead of reading files line by line, you select any node on the canvas and ask Flowy to explain it, evaluate it for architectural problems, or propose how it should be restructured. All three capabilities operate directly on the code graph that Flowy has already built — meaning the AI understands the context of your whole repository, not just an isolated file.

## How Explain with AI works

The explanation flow is designed to be instant and contextual — one click, one answer.

<Steps>
  <Step title="Select a node">
    Click any node on the mind map canvas. The node highlights and a side panel slides in from the right, showing the file path, export list, and direct dependency count.
  </Step>
  <Step title="Trigger the explanation">
    Click the **Explain with AI** button in the side panel (or press `E` with the node focused). Flowy bundles three data sources and sends them to the model: the file's raw source, its list of imports, and the names of every other node that imports it.
  </Step>
  <Step title="Read the plain-language summary">
    Within a few seconds the panel updates with a structured explanation covering: what the module does, what it depends on, what depends on it, and any immediate observations the model flags as noteworthy.
  </Step>
  <Step title="Follow related nodes">
    The explanation panel includes clickable references to every module mentioned. Clicking one re-centres the canvas on that node and queues its explanation automatically.
  </Step>
</Steps>

<Tip>
  Use **Explain with AI** on unfamiliar entry points — such as `index.ts` or `app/layout.tsx` — when onboarding to a new codebase. The explanation surfaces the dependency chain from the top down, giving you a mental model before you dive into individual files.
</Tip>

## Anomaly Detection explained

Anomaly Detection runs as a background analysis pass every time a map is synced. It evaluates two primary signals for every module in the graph:

**Inverse cohesion** measures how many distinct responsibilities a single file appears to own. A cohesive module does one thing; a module with high inverse cohesion does many unrelated things. Flowy estimates this by analysing the spread of import namespaces and the variance in the types of symbols the file exports (data models, side-effect utilities, UI components, and so on mixed together in one file are a classic signal).

**Incoming dependency count** counts how many other modules import a given file. A file imported by twenty other modules is a load-bearing wall in your architecture. If it also has high inverse cohesion, it is simultaneously fragile and critical — the definition of a structural risk.

When either signal crosses a configurable threshold, the node on the canvas is decorated with an amber warning badge. Opening the node panel shows a concise breakdown of which signal triggered the flag and how far above the threshold the module sits.

<Accordion title="What thresholds trigger an anomaly flag?">
  Default thresholds are calibrated against typical TypeScript/JavaScript project patterns:

  - **Incoming dependencies ≥ 15** on a non-utility module triggers a flag
  - **Inverse cohesion score ≥ 0.7** (on a 0–1 scale) triggers a flag
  - **Both signals elevated simultaneously** triggers a critical flag (red badge instead of amber)

  These thresholds will be user-configurable in a future release — see the [roadmap](/reference/roadmap) for details.
</Accordion>

## Refactor Suggestions

When the AI detects a Single Responsibility Principle (SRP) violation, it does not just report the problem — it proposes a remediation path.

The SRP states that a module should have one, and only one, reason to change. Violations occur when a file mixes concerns: for example, a component file that also contains data-fetching logic, type definitions, and a utility function used only by a sibling file.

**How the suggestion is generated:**

1. The model groups the file's exports by inferred concern (UI rendering, data access, pure computation, type definitions, and so on).
2. It proposes a split: which exports should move to which new files, and what those new files should be named following the project's existing naming conventions.
3. It lists every import in the codebase that will need updating, so you know the full blast radius of the refactor before you start.

<Note>
  Refactor Suggestions are recommendations, not automated rewrites. Flowy presents the proposal in the side panel; applying it is always a deliberate, manual action on your part. This keeps the AI in an advisory role and you in control of every change that reaches your repository.
</Note>
