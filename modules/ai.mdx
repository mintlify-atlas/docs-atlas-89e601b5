The Integrated AI module turns your mind map from a passive diagram into an active analytical partner. Instead of reading files line by line, you select any node on the canvas and ask Flowy to explain it, evaluate it for architectural problems, or propose how it should be restructured. All three capabilities operate directly on the code graph that Flowy has already built — meaning the AI understands the context of your whole repository, not just an isolated file.

## Explain with AI

The explanation flow is designed to be instant and contextual. Select any node on the mind map canvas and trigger the AI explanation to receive a plain-language summary of that module's responsibility — what it does, what it depends on, and why it matters in the context of your repository.

This is especially useful when onboarding to an unfamiliar codebase. Starting from an entry point like `index.ts` and explaining outward through its dependencies gives you a mental model of the architecture before you dive into individual files.

## Anomaly Detection

Anomaly Detection evaluates every module in your graph for two primary signals:

**Inverse cohesion** measures how many distinct responsibilities a single file appears to own. A cohesive module does one thing; a module with high inverse cohesion mixes unrelated concerns — data models, side-effect utilities, and UI components in the same file are a classic signal.

**Incoming dependency count** counts how many other modules import a given file. A file imported by many other modules is a load-bearing wall in your architecture. When it also has high inverse cohesion, it is simultaneously fragile and critical — the definition of a structural risk.

When either signal is elevated, the AI flags the module so you can investigate it before it becomes a bottleneck. The flag appears directly on the canvas, keeping problem areas visible as you navigate the map.

## Refactor Suggestions

When the AI detects a Single Responsibility Principle (SRP) violation, it does not just report the problem — it proposes how to extract and decouple the affected modules.

The SRP states that a module should have one, and only one, reason to change. Violations occur when a file mixes concerns: for example, a component file that also contains data-fetching logic, type definitions, and utility functions used only by sibling files.

The model surfaces a concrete suggestion for how to split the module — which responsibilities should be separated and how the resulting structure would reduce coupling across the graph. Reviewing the suggestion directly in the canvas gives you the full picture of the change before you begin any work in your editor.
